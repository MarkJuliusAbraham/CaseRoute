      Overview

      CaseRoute is a study of reliable case submission and processing. A generator plays thousands of customers submitting support cases; the backend accepts them, saves them, and hands them to a separate processor; the results come back and are recorded on each case. Four applications, two pieces of infrastructure:

      1. Generator sends POST /api/cases (or /direct) on a fixed schedule.
      2. Backend accepts it: into Kafka (cases.submitted, reply 202) or straight into PostgreSQL (reply 201).
      3. Saving a case also writes an outbox row in the same transaction; the outbox relay publishes it to cases.saved.
      4. Processor reads cases.saved, simulates the work, and publishes the result to cases.processed.
      5. Backend reads cases.processed and records ROUTED or FAILED on the case.
      6. Checker (in the generator) compares what each client was told with what the system recorded.

      Guarantees

      • Idempotent by clientRequestId. Every submission carries a client-chosen UUID with a unique index on it. Resending never creates a second case, so clients may retry when unsure.
      • No dual writes. A case and its "case saved" event commit together (outbox), so a saved case is always handed to processing.
      • At-least-once messaging, exactly-once effect. Kafka may redeliver; every consumer's write is idempotent (insert ignores duplicates, result updates only an OPEN case).
      • Nothing silently dropped. Unreadable messages go to a .DLT topic instead of blocking or vanishing.

      Architecture FAQ

      Organised by component. For each: what it is for, then every lever it has: where it is set (the dashboard, or a property for the next restart), what it trades, and what was measured here. Defaults are in brackets.

      Generator · Backend · Kafka · Processing · Across the system

      Generator

      Plays the customers: sends submissions on a fixed schedule, records what each was told, and checks the result.

      What is the generator for, and why is it open-loop?
      It models real customers, who keep submitting whatever the backend's speed. It never waits for replies before sending the next submission, so overload shows up as it would in production: as slow replies, skips and unknown outcomes, not as a politely slower test. It also holds the client's side of the record, which is why the checker lives here.
      Rate, duration and "Run until stopped"
      Dashboard [50/min, 1 min; presets 100k, 200k, 500k]. The demand. Up to 1,000,000 per minute for up to 60 minutes, or until stopped. Memory stays flat however long it runs, so endless runs show whether anything builds up over time. Measured: the system keeps up to about 9,000–11,500 per second (550k–700k per minute); above that the generator skips what does not fit.
      Warm-up
      Dashboard [30 s]. Ramps from zero to the full rate against an endpoint that takes the real Kafka path but stores nothing, so the run starts on open connections, compiled code and a warm producer. 0 tests a cold start. Measured: without it, even 500k failed in the first second, opening thousands of connections at once.
      In-flight limit
      Dashboard [no limit]. Caps submissions awaiting a reply; above it a submission is skipped, not queued. A blunt client-side brake: it protects the backend but turns excess demand into skips at a fixed concurrency rather than a fixed wait.
      HTTP client
      Dashboard [Jetty]. Jetty: 8 instances sharing a fixed pool of 2,000 connections. Java's built-in client: 8 instances, collapses near 10,000 per second (lock contention and connection bursts that exhaust Windows' local ports). Config: generator.jetty.clients [8] (16 measured worse), max-connections [2,000], selectors [1].
      Waiting line (generator.jetty.max-queued)
      Config [40,000, about 4 s of work]. Requests wait here for a free connection; with no room they are skipped, never sent. Sized by time, not kept short: it must absorb stalls (the warm-up switch, a GC pause) yet stay far below the 15 s request timeout, because each timeout closes a connection and holds a port for 2 minutes. Measured: 100,000 let waits reach the timeout; 10,000 turned every brief stall into skips, even at 500k.
      Connection lifetime (generator.jetty.idle-timeout)
      Config [0: never closed]. A fixed pool: opened gradually during the warm-up, then kept. Measured: a 30 s idle timeout shrank the pool in calm periods, and the next slowdown opened 874 connections in one second; about 2,750 requests were refused. The dashboard's Connections card shows opened and closed after the warm-up; both should stay 0.
      Retry unknown outcomes (during the run)
      Dashboard [off]. Resends an Unknown outcome with the same ID, up to 5 attempts, waits doubling from 0.5 s to 8 s with jitter (generator.retry.*). Safe because the backend is idempotent, but it adds load during overload, and a submission holds its in-flight slot until its final outcome.
      Retry period (after the run)
      Dashboard [off; 120 s], or Retry now. Resends everything still Skipped, Blocked or Unknown in passes at the run's rate, until none is left, the time limit, 10 passes, a pass that changes nothing, or Stop. Keeps the run's measured time clean while still finishing the job. Measured: a 1M run accepted 739,711 during the run; the retry period recovered the other 260,289 in 23 s.
      Pause when the backend is down (circuit breaker)
      Dashboard [on]. After 20 replies in a row that never reached the backend (refused, broken or timed out), the generator stops sending, waits 1 s (doubling up to 10 s while the backend stays away), sends one probe, and when the backend answers ramps back up over 5 s. The schedule keeps running: submissions due meanwhile are skipped with the reason, and the retry period can send them later. Without it, a down backend is hit at full rate with requests that all fail, and a returning one with a wall of connections and retries.
      How are connection errors classified?
      Not a lever but a rule: "connection refused" means the request never reached the backend, so it is Skipped (not sent, nothing stored) and safe to resend. A connection that breaks mid-request, or a timeout, is Unknown: the backend may have it. Only Unknowns need the checker to say what really happened.
      Duplicate submissions
      Dashboard [0%]. Sends up to 50% of submissions a second time with the same ID and content, 0–2 s later, like a double click. Tests the system's idempotency; the checker verifies each still has one case, processed once.
      Intake path and Connection test
      Dashboard (Backend card) [through Kafka]. Chooses the endpoint the generator calls: POST /api/cases (Kafka, 202), /direct (saved before the reply, 201), or /noop (instant 202, nothing stored). The connection test measures the generator and the backend's web server alone: about 15,000 per second from the generator, 25,210 from the native tool oha.

      Backend

      The only writer of PostgreSQL: accepts submissions, saves them, hands them to processing through the outbox, and records results.

      What is the backend for, and where does it wait?
      It turns a submission into a promise (202 after Kafka confirms) and later into a case. Each intake request waits for Kafka's confirmation, so the backend's capacity is about how many requests can wait at once and how fast confirmations come back, not about CPU: it used 3–4 of 20 cores at its ceiling.
      Load shedding
      Dashboard [off; 1,000 at once]. Over the limit, a filter answers 503 with Retry-After: 1 before doing any work: Blocked, a definite "nothing stored, try later". Turns overload into fast, safe refusals instead of slow replies. The limit should sit just above what the backend can have in progress at full speed.
      Process after intake
      Dashboard (Processor card) [on]. Pauses the case writer, the outbox relay and the result writer (and the processor). Intake keeps accepting; everything waits in Kafka and catches up on resume. Isolates intake for measurement. Measured: pausing it did not raise intake (about 8,700/s either way).
      Request threads (spring.threads.virtual.enabled)
      Config [on]. A virtual thread per request, so thousands can wait for Kafka cheaply. Measured: Tomcat's 200-thread pool ran out near 600k per minute (200 threads / ~20 ms per confirmation).
      Connections (server.tomcat.*)
      Config. accept-count [2,000] is the queue of connections waiting to be accepted (Windows may cap it lower); max-keep-alive-requests [-1] and keep-alive-timeout / connection-timeout [-1] mean a connection is never closed by the backend, matching the generator's fixed pool. Fine for a known client, not for the internet.
      Kafka confirmation timeout (caseroute.kafka.publish-timeout)
      Config [10 s]. How long an intake request waits for Kafka before answering 503 (Unknown to the client: the message may still have been written).
      Graceful shutdown (server.shutdown)
      Config [graceful, up to 20 s]. On a normal stop the web server refuses new connections, lets requests in progress finish and reply, then Kafka and the database close. A planned restart then leaves no request in doubt; without it, requests in progress were cut off.
      Downtime test
      Dashboard (Backend card): Stop gracefully or Crash, then restart the backend from IntelliJ. Graceful: every request in progress gets its reply; clients only see refused connections (not sent). Crash: the process exits instantly; requests in progress get no reply and are Unknown, and the checker shows how many were saved anyway (Kafka had them) and that none became a second case after the retry period resent them.
      Case writer (spring.kafka.listener.concurrency, max-poll-records)
      Config [3 consumers, 500 per batch]. Reads cases.submitted and saves each batch in one statement, duplicates ignored. Three consumers means more than 3 partitions add no saving parallelism.
      Outbox relay (caseroute.outbox.batch-size, poll-interval-ms)
      Config [batches of 1,000, every 100 ms]. Publishes saved-case events to cases.saved; while batches come back full it keeps going instead of waiting for the next tick. Bigger batches mean fewer round trips to PostgreSQL and Kafka. The dashboard's "awaiting relay" count shows it falling behind.

      Kafka

      The durable buffer between every stage: the promise behind a 202, and the backlog when a later stage is slower or paused.

      What is Kafka for here?
      It decouples speeds. Intake only needs Kafka's confirmation; saving and processing read at their own pace. One broker in Docker; topics cases.submitted, cases.saved, cases.processed, cases.warmup and .DLT topics for unreadable messages. Measured: the broker took 185,528 confirmed writes per second on its own, so it is not the limit.
      Intake producers: count
      Dashboard (Kafka panel, between runs) [1]. Each producer has one network thread, one connection and up to 5 requests awaiting confirmation; submissions are spread over them in turn. Measured: 4 producers were worse (about 7,500 per second against 9,000).
      Linger and batch size
      Kafka panel [5 ms, 16 KB; resets on backend restart]. How long the producer waits to fill a batch, and how big one may get. Bigger batches mean fewer requests and fewer wake-ups of the producer's network thread, but every submission waits up to the linger time. Measured at 900k: 25 ms with 64 KB gave about 9% more than the defaults; 50 ms with 256 KB was worse.
      Compression
      Kafka panel [none]. Shrinks batches at the cost of CPU on the backend and the broker. Helps when bytes are the limit; here the broker is local and messages are small. Not measured.
      Requests in flight
      Kafka panel [5, the maximum with idempotence]. Requests per producer awaiting confirmation. Lower only to test the effect; 5 is the safe maximum.
      Delivery guarantee (acks=all, idempotence)
      Fixed on purpose. A 202 is sent only after the broker has the message, and a producer retry never writes it twice. This is what makes an accepted submission certain to be stored; turning it off would be faster and would break the promise.
      Partitions
      Kafka panel, add-only [6 per topic]. Units of parallelism for consumers, and how producer batches are split. Kafka cannot remove partitions: going back means recreating the topic. Measured: 12 partitions were slower than 6 for intake (smaller batches per request), and the backend reads with 3 consumers, the processor with 6.
      Retention (caseroute.kafka.retention, segment)
      Config [6 h, 1-hour segments; warm-up 1 h]. How long messages stay, read or not. Long enough to replay a run's backlog, short enough that load tests do not fill the disk.
      Live producer metrics: how do I read them?
      Kafka panel. High "waiting in producer" with requests in flight at the cap: the producer is the bottleneck. High "broker confirmation" with the broker idle: the time is lost between the producer and the broker. Measured: confirmations grew from ~5 ms to ~150 ms under load while Kafka's CPU stayed low; a recording traced it to the producer's network thread blocked on a lock in Java's Windows networking code (about 25% of the time).

      Processing

      The slow, failure-prone downstream system: turns a saved case into a routed or failed one, through Kafka only.

      What is the processor for, and why is it separate?
      It models real downstream work with its own speed and failures, so the rest of the system must tolerate both. It has no database access: it reads cases.saved, works, and publishes to cases.processed; the backend records the result, only on a case still OPEN, and counts every result it receives.
      Concurrency (caseroute.processing.consumers, max-in-flight)
      Config [6 consumers, 20,000 cases in flight]. Each case runs on its own virtual thread, so throughput is about in-flight / time per case (~18,000 per second at ~1.1 s). When the limit is reached it stops fetching and the backlog waits in Kafka. Offsets only advance past finished cases, so a crash redelivers unfinished ones.
      Simulated work (caseroute.processing.*)
      Config [~1 s per case (0.5–1.5 s); 1% take 10 s; 2% transient errors retried after 500 ms, up to 3 attempts; 0.1% fail permanently]. Each case's behaviour is derived from its ID, so a redelivered case behaves the same and runs are reproducible.
      Process after intake
      Dashboard [on]. Pauses fetching from cases.saved; cases in progress finish and the backlog waits in Kafka. Driven together with the backend's pause.
      Failure handling
      Not a lever but a design choice: transient errors are retried inside the processor; permanent failures produce a FAILED result and a copy in cases.saved.DLT. A duplicate result is harmless for the case, and visible to the checker as "processed more than once".

      Across the system

      Promises that no single component keeps alone.

      What does a 202 promise, and how is it checked?
      That the submission is durably in Kafka and will become a case. The checker's "Accepted but missing" counts broken promises and must be 0; "Unknown, saved anyway" shows replies that were lost while the case was not.
      How do duplicates stay harmless end to end?
      The client chooses the ID. A unique index keeps one case; only a newly saved case gets an outbox row, so a repeat never reaches processing; results update only an OPEN case. The checker counts cases created twice and cases processed more than once; both must be 0.
      What happens when the backend goes down?
      With one backend instance, intake stops: Kafka sits behind the backend, so nothing reaches it. Clients see refused connections (not sent) and, for requests in progress at the moment of a crash, no reply (Unknown). What limits the damage: graceful shutdown for planned stops, the generator's circuit breaker (pause, probe, ramp up), the retry period resending with the original IDs, and idempotency, so a resend of a request that was in fact saved does not create a second case. Staying available during an outage needs a second instance behind a load balancer.
      Why the outbox?
      Saving a case and announcing it are writes to two systems. The outbox row commits with the case, and a relay publishes it afterwards, so a saved case is never left unannounced. The price is at-least-once delivery, which every consumer tolerates.
      What is deliberately not production-grade?
      One Kafka broker with replication factor 1: while it is down, intake stops (503, Unknown to the client), and losing its disk would lose accepted submissions not yet saved. One backend instance. Everything, including the load generator, on one Windows machine. Connections never closed for being idle. No authentication. Schema managed by Hibernate (ddl-auto=update), not migrations.
      How would it scale beyond one machine?
      Several backend instances behind a load balancer, each with its own producers. A Kafka cluster with replication 3 and min.insync.replicas=2. More partitions together with more consumers. The load generator on separate machines. Servers on Linux.

      Why: the intake producer's network thread waits on a lock

      A Java Flight Recorder recording of the backend during a 900k run showed the Kafka producer's single network thread blocked about a quarter of the time, 2.3–2.5 s in every 10 s and up to 284 ms at once, waiting for a lock inside Java's Windows network selector (WEPollSelectorImpl.clearInterrupt). Every message that starts a new batch wakes that thread up, and on Windows the wake-up is a small write over a local socket made while holding the same lock. While the thread is stuck, every request waiting for Kafka waits too: confirmations grew from about 5 ms early in the warm-up to about 150 ms. Tomcat's connection poller showed the same wait. Linux implements the wake-up far more cheaply, so running the backend on Linux (WSL or a container) is the open test of this explanation. Larger batches (linger 25 ms, 64 KB) mean fewer wake-ups and gave about 9% more.

      How we got here

      Java's HTTP client in the generator
      Collapsed near 10,000 requests/s: lock contention and a burst of new connections exhausted Windows' 16,384 local ports. Replaced by Jetty (8 instances, 2,000 connections).
      Connection churn
      Request timeouts and idle timeouts each closed connections and reopened them in bursts. Fixed with a fixed pool (no idle closing on either side) and a waiting line sized to ~4 s, far below the timeout.
      Generator and backend freezes
      Tomcat's low-priority utility threads starved under load on Windows; -XX:-UseThreadPriorities. Thread dumps froze the generator for up to 12 s; use Java Flight Recorder instead.
      Warm-up
      Without it, the first second at full rate opened thousands of connections at once.
      Virtual threads and a separate intake producer
      The 200-thread pool ran out around 600k/min; customer sends no longer wait behind the relay.

      Running a load test reliably

      • Close heavy programs first. Everything shares one machine's CPU and networking.
      • Restart the backend, generator and processor after code changes, from IntelliJ. DevTools auto-restart is off, so a recompile never restarts the backend mid-run.
      • Use a 30-second warm-up (the default). Let the pipeline drain between runs: a backlog being processed competes with the next run for the machine.
      • Watch the Outcomes section's Connections: opened and closed after the warm-up should stay 0.
      • Never take thread dumps of the generator during a run; they freeze it for up to 12 s. Use Java Flight Recorder (jcmd <pid> JFR.start settings=profile), about 1–2% overhead.
      • To isolate a layer, use the Connection test toggle (nothing behind the backend), untick Process after intake (intake only), or watch the Kafka panel's live producer metrics.

      What each part shows

      Presets
      The Generator card's Preset list fills every run setting for a common stress test: Smoke test, Baseline load, Find the ceiling, Overload and recover, Cold spike, Soak (until stopped), Duplicates and retries, Backend failure drill, Generator ceiling (connection test). Each shows what it tests and what to look for. You can change anything before starting (the description then says "modified"). Live controls (load shedding, pausing downstream work, the Kafka panel) are left as they are.
      Service settings
      Generator: rate (presets 100k, 200k, 500k), duration or run until stopped, warm-up (30 s by default), in-flight limit, retries during the run, the retry period after it, duplicate submissions and the HTTP client. Backend: the intake path (through Kafka or direct), the Connection test toggle, Load shedding with its limit and live count of turned-away submissions, and the database reset. Processor: the Process after intake toggle, which pauses everything after intake in both apps. Kafka: the intake producers, partitions and live producer metrics (see Kafka & PostgreSQL). Badges show each service's health check.
      Run controls
      Start and stop a run, and Retry now after it. Stop also ends a retry period. Progress streams from the generator over server-sent events every 500 ms, including during a retry period.
      Request pipeline
      An animated graph of the pipeline. Counts come from the run (sent, including the retry period's sends; accepted) and from the backend's per-run stats polled every second (saved, open, routed, failed, in the outbox). The animation is illustrative; the numbers are measured.
      Outcomes
      One bar for every planned submission, split by its current outcome: accepted, no definite answer (skipped, blocked or unknown: what a retry period sends again), rejected, not sent (stopped early), and still to come during the run. The parts always add up to the plan. Below it, three cards: During the run (sent, accepted by the run itself, in flight, and the in-run retries when on), Retry period (passes, sent, recovered, what is still unresolved, and each pass's result), and Connections (Jetty's pool; opened and closed after the warm-up should stay 0).
      Checker
      The reconciliation result for the run (see Generator).
      Inspect data
      Saved cases (paged, CSV download), the latest 100 responses, and health history kept in this browser for 24 hours.

      Generator

      Plays the customers. Submissions are sent with Jetty's HTTP client by default (8 instances sharing a fixed pool of 2,000 connections); Java's built-in client remains as an option and collapses near 10,000 requests per second. It is open-loop: submissions are sent on a fixed schedule whatever the backend's speed, as real customers would, each on its own virtual thread. Only one run at a time; the latest run stays in memory and every run is written to reports/<runId>.jsonl.

      Run settings

      requestsPerMinute, durationMinutes, endless
      Up to 1,000,000 per minute, for up to 60 minutes. With endless ("Run until stopped") the run keeps going until stopped and the duration is ignored. Memory stays flat either way: submission n's ID is the run id plus n, so no list of submissions is kept, and only outcomes other than accepted are stored.
      maxInFlight
      Optional cap on submissions awaiting a reply; above it a submission is skipped, not queued. Null means no cap.
      submissionMode
      KAFKA posts to /api/cases and expects 202; DIRECT posts to /api/cases/direct and expects 201 (or 200 for a retry of an already saved case); NOOP (the "Connection test" toggle) posts to /api/cases/noop, warm-up included, and expects 202 with nothing stored.
      httpClient
      JETTY is the default. JDK: Java's built-in HttpClient, spread over 8 instances; it collapses near 10,000 requests/s. JETTY: Jetty's HttpClient as 8 instances, each with its own network thread and waiting line, together at most 2,000 connections to the backend; extra requests wait in short queues (40,000 in total, about 4 s of work) instead of opening new connections, and a request with no room is skipped, never sent (generator.jetty.*). With a single instance, a large backlog left nearly all of Jetty's worker threads queued on its one waiting-line lock. The pool is fixed: with a warm-up, Jetty opens all its connections gradually over the warm-up's second half (opening hundreds at once at the switch was refused by the backend's accept queue), and neither side ever closes them for being idle. With a 30 s idle timeout the pool shrank during calm periods, and the next brief slowdown opened 874 connections in one second, of which about 2,750 requests were refused. Outcomes are classified the same either way.
      retryEnabled
      Resend submissions whose outcome is unknown. Off by default.
      circuitBreaker
      On by default. After 20 replies in a row that never reached the backend, pause sending, probe after 1 s (doubling up to 10 s), and ramp back up over 5 s when it answers. Submissions due meanwhile are skipped with the reason. The Outcomes section shows whether the backend is reachable, how often sending paused and how many submissions were held back.
      retryPeriod, retryPeriodSeconds
      After a run that finishes by itself, send every submission still Skipped, Blocked or Unknown again (see Retry period). Off by default; up to 120 s by default.
      duplicatePercent
      0 to 50: that share of submissions is sent a second time with the same ID and content, 0 to 2 s after the first. Extra traffic, not extra submissions; the checker verifies each still has one case, processed once.
      warmupSeconds
      Before the measured run, ramp from zero to the full rate over this many seconds against POST /api/cases/warmup, which goes through the same path as a real submission, Kafka write included, but to a topic nothing consumes, so no case is created. That is rate × seconds ÷ 120 requests, counted separately. The run then starts at full rate on already open connections, with warmed-up code and a warmed-up Kafka producer. 0 (default) starts cold, like a sudden spike.

      Outcomes

      Accepted
      The expected status with matching fields.
      Failed / mismatched
      A definite answer that was not acceptance: 4xx, or a reply with the wrong fields.
      Unknown
      Timeout (15 s), a connection that broke mid-request, or 5xx. The case may or may not exist; only the checker can tell. A refused connection is not Unknown: it never got in.
      Skipped / not sent
      Skipped: never sent, because the in-flight cap or the HTTP client's waiting line was full, the connection was refused (the backend was not listening), or sending was paused because the backend was down. Nothing can have been stored. Not sent: the run was stopped first.
      Blocked
      Turned away by the backend's load shedding: a 503 with Retry-After, meaning "busy, nothing stored". Unlike Unknown, it is a definite answer, so it is safe to resend. It is never retried during the run, even with retries on, so the run stays exactly its set length; the retry period after the run sends it again.

      Retry period

      A layer after the run: every submission without a definite answer is sent again, with its original clientRequestId. Skipped (never sent), Blocked (busy, nothing stored) and Unknown (may or may not be stored) qualify; resending is safe because the backend ignores an ID it already has. Rejected and mismatched submissions are not retried, since the backend already gave a definite answer, and Not sent is what you stopped. With retryPeriod on, it starts by itself after a run that finishes on its own; Retry now (POST /api/runs/{id}/retry) starts one by hand. It sends at the run's rate in passes, waiting 1 s, 2 s, 4 s ... (at most 30 s) between them, and ends when nothing is left, after retryPeriodSeconds (default 120), after 10 passes, when a pass resolves nothing (the backend may be down), or when stopped. It is not part of the run's measured time. New outcomes replace the old ones in the run's counts, so the checker sees the final state. Per-pass results are in the snapshot's retry field and in reports/<runId>.retry-<n>.json.

      Retries

      With retries on, an unknown outcome is resent with the same clientRequestId, up to 5 attempts in total. Waits double from 0.5 s to a cap of 8 s, each randomised between half and all of its value so clients that failed together do not retry together. A submission keeps its in-flight slot until its final outcome. Rejections are never retried. Tune with generator.retry.max-attempts, base-delay and max-delay. Retries are safe because the backend is idempotent, but they add load: under sustained overload they can deepen it.

      Checker

      Reconciliation: after a run, it streams the backend's ledger of saved cases for the run (GET /api/simulation/cases/ledger) and compares it with the outcome the generator recorded for every submission. It runs automatically once processing settles, can be repeated, and writes reports/<runId>.check.json.

      Accepted: processed / awaiting / missing
      Missing is the alarming one: the client was promised a case that does not exist. Checked too early, it may still be waiting in Kafka.
      Unknown: saved anyway / never arrived
      Shows what "unknown" really meant. Saved anyway: the reply was lost, not the case.
      Blocked: total / saved
      Submissions still blocked after any retry period. "Blocked but saved" should always be 0: the backend turned them away before doing anything.
      Rejected but saved, unexpected
      Should always be 0: a case the client was told failed, or one it never sent.
      Cases in the database
      Cases saved for this run. However often a submission was sent (repeats, retries, the retry period), it should have one case, so this is at most the number of submissions.
      Repeated submissions, cases created twice, processed more than once
      With Duplicate submissions set, the generator sends that share of submissions a second time with the same ID and content, 0 to 2 s after the first. "Cases created twice" counts extra cases for an ID that already has one, and "Processed more than once" counts cases (of all in the run) that received more than one processing result, recorded by the backend per case. Both should be 0: the unique index on clientRequestId keeps one case, and only a newly saved case is handed to processing. A Kafka redelivery after a crash can make the second one non-zero without a bug. A dash means the backend predates this count.

      Verdict: Consistent (every accepted case saved and processed), Still processing (no problems, some still OPEN), or Discrepancies found.

      The checker only concludes anything from a complete ledger: the backend ends it with its own row count (#end,<rows>), and a ledger without it, or with a different count, is refused with "ended early: check again" instead of a verdict. Before this, the backend cut streamed downloads off after 30 s without an error (now 10 minutes, spring.mvc.async.request-timeout): a million-case ledger read just after a crash-restart stopped at 100,441 rows, and the rest were reported as missing although every case had been saved and processed.

      The checker lives in the generator because only the client knows what it was promised. It reads the system's side through the backend's API, not the database, so it audits from the outside. A separate application would add a process without adding independence.

      Run report

      One JSON object per line: run (settings), plan (the planned count and how IDs are formed), result (only submissions that were not accepted), notSent (the range never sent), second (per-second counts, latency avg, p99, max, and connections opened and closed) and summary. Written by a background thread so disk I/O never delays sending.

      Backend

      Spring Boot service that owns the cases and outbox tables. It is the only application that touches PostgreSQL.

      Public API

      POST /api/casesKafka intake. Waits only for Kafka to confirm the message, then replies 202 with a Location header for the status lookup. 503 if Kafka does not confirm within 10 s.
      POST /api/cases/directDirect intake. Saves the case and its outbox row in one transaction, replies 201. A retry of a saved submission replies 200 with the existing case; the same ID with different content is a 409.

      Inside

      Load shedding
      Off by default. When on, a filter that runs before anything else (security, parsing, Kafka) lets at most maxConcurrent submissions be worked on at once (POST /api/cases, /direct, /noop; never the warm-up). Any beyond that get 503 with Retry-After: 1 immediately. The Retry-After header is the contract: nothing was stored, so it is safe to resend. A 503 without it (Kafka did not confirm) still means the outcome is unknown. A restart turns it off.
      Request handling
      Tomcat with a virtual thread per request (spring.threads.virtual.enabled). Before that, the 200-thread pool ran out around 600k per minute, because every request thread waits for Kafka's confirmation. Up to 8,192 connections plus a queue of 2,000 waiting to be accepted. Idle connections are never closed (server.tomcat.keep-alive-timeout=-1, connection-timeout=-1), matching the generator's fixed pool. DevTools auto-restart is off, so a recompile never restarts the backend mid-run.
      Kafka producers
      Two kinds, each with its own buffer, network thread and connection. The intake producers (backend-intake-N, one by default; count, linger, batch size, compression and requests in flight are adjustable between runs in the Kafka panel) carry customer submissions and warm-ups, where every request waits for its own confirmation. The other carries background work: the outbox relay's bursts and dead letters. A producer has exactly one network thread, so customer traffic never waits behind the relay.
      Submission consumer
      Group case-writer, 3 threads, batches of up to 500 from cases.submitted. One SQL statement per batch inserts the cases (duplicates ignored) and their outbox rows. Unreadable messages go to cases.submitted.DLT.
      Outbox relay
      Every 100 ms, claims up to 1,000 outbox rows (FOR UPDATE SKIP LOCKED), publishes them to cases.saved keyed by case ID, waits for Kafka, then deletes them. A crash before the delete republishes; the processor tolerates that.
      Result consumer
      Group case-result-writer on cases.processed. Records status, category, team and attempts, only on cases still OPEN, so a redelivered result changes nothing. Every result is also counted on the case (results_received), so a check can see a case processed more than once. Unusable results go to cases.processed.DLT.
      Pausing downstream work
      GET/PUT /api/simulation/pipeline (local only) pauses the case writer, the outbox relay and the result writer, for experiments that isolate intake. The dashboard's "Downstream processing" toggle drives it together with the processor's. Nothing is lost while paused, and a restart turns it back on.
      Graceful shutdown
      server.shutdown=graceful: a normal stop refuses new connections, lets requests in progress finish and reply (up to 20 s), then closes Kafka and the database. The dashboard's Downtime test can stop the backend this way, or crash it, for comparison.
      Status constraint
      On startup, the cases_status_check constraint is rebuilt from the status enum, since Hibernate never updates one it created.

      Processor

      A separate Spring Boot application that works purely through Kafka: it reads cases.saved, simulates the work, and publishes each result to cases.processed. It has no database access; the backend records results.

      Concurrency

      Six Kafka consumers (one per partition), each on its own thread, fetch up to 2,000 messages and start every case on its own virtual thread, up to 20,000 in flight. Cases finish in any order, so a slow case never holds back the rest. Per partition, the committed offset only advances to the oldest case still running: after a crash, unfinished cases are redelivered and none is skipped. When the in-flight limit is reached, consumers pause fetching and the backlog waits in Kafka.

      Simulated work

      Each case's plan is derived from its clientRequestId, so a redelivered case behaves the same way. Defaults (caseroute.processing.*):

      • Takes 0.5 to 1.5 s (mean 1 s); 1% are slow and take 10 s.
      • 2% chance per attempt of a transient error, retried after 500 ms, up to 3 attempts; exhausting them fails the case.
      • 0.1% fail permanently.
      • Routed by category: Billing Support, Technical Support or Account Services.

      Failed cases are also copied to cases.saved.DLT with the reason in a header. The work is Thread.sleep: it models waiting on other systems, not CPU, so throughput is roughly in-flight cases divided by time per case.

      Port 8083 (local only); GET /actuator/health. GET/PUT /api/pipeline pauses or resumes fetching from cases.saved: cases already in progress finish, and the backlog waits in Kafka. Driven by the dashboard's "Downstream processing" toggle.

      Kafka & PostgreSQL

      Both run in Docker Compose (docker compose up -d). docker compose down keeps the data volumes; add -v to delete them.

      Kafka topics

      Created by the backend at startup. Kept for 6 hours (1-hour segments), whether consumed or not.

      TopicPartitions (at creation)Producer → consumer
      cases.submitted6Backend intake → backend submission consumer
      cases.saved6Outbox relay → processor
      cases.processed6Processor → backend result consumer
      cases.warmup6Warm-up endpoint → nobody (kept 1 hour)
      *.DLT1Unreadable or failed messages, for inspection

      Producers use acks=all with idempotence. Kafka UI: localhost:8082.

      Kafka panel

      Changes apply between runs only: the panel locks during a run, and the backend refuses changes while submissions are waiting for Kafka (409).

      • Intake producers (PUT /api/simulation/kafka/producer): how many producers write customer submissions and warm-ups (1 to 8, used in turn), and their linger, batch size, compression and requests in flight. One producer has one network thread, one connection and at most 5 requests awaiting confirmation; a 900k run measured its ceiling at about 9,700/s (5 x ~290 records / ~150 ms per confirmation), with Kafka's CPU low. Applying replaces the producers; the old ones send what they hold first. Lasts until the backend restarts, which goes back to application.properties. acks=all and idempotence are fixed, since they are what makes an accepted submission certain to be stored.
      • Partitions (PUT /api/simulation/kafka/partitions): add-only, because Kafka cannot remove partitions. cases.warmup follows cases.submitted. Producers and consumers refresh topic metadata every 10 s (metadata.max.age.ms, Kafka's default is 5 minutes), so new partitions are used before the next run. The backend reads with 3 consumers per topic, so more partitions add no reading parallelism there.
      • Producer, live (GET /api/simulation/kafka/metrics): the intake producer's own metrics over the last ~10 s. Time waiting in the producer points at batching or the in-flight limit; time waiting for the broker's confirmation points at Kafka itself.

      PostgreSQL

      Database caseroutedb on localhost:5432; pgAdmin on localhost:5050.

      cases
      One row per case; unique client_request_id, indexed test_run_id, status plus the processor's result columns and results_received (processing results that arrived; 1 when processed once).
      outbox
      "Case saved" events waiting to be published. Normally near empty; a growing count means the relay is behind.
      Runs target the backend configured on the generator server. Reports remain on disk; progress is retained in memory for the latest run.
