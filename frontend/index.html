    Overview

    CaseRoute is a study of reliable case submission and processing. A generator plays thousands of customers submitting support cases; the backend accepts them, saves them, and hands them to a separate processor; the results come back and are recorded on each case. Four applications, two pieces of infrastructure:

    1. Generator sends POST /api/cases (or /direct) on a fixed schedule.
    2. Backend accepts it: into Kafka (cases.submitted, reply 202) or straight into PostgreSQL (reply 201).
    3. Saving a case also writes an outbox row in the same transaction; the outbox relay publishes it to cases.saved.
    4. Processor reads cases.saved, simulates the work, and publishes the result to cases.processed.
    5. Backend reads cases.processed and records ROUTED or FAILED on the case.
    6. Checker (in the generator) compares what each client was told with what the system recorded.

    Guarantees

    • Idempotent by clientRequestId. Every submission carries a client-chosen UUID with a unique index on it. Resending never creates a second case, so clients may retry when unsure.
    • No dual writes. A case and its "case saved" event commit together (outbox), so a saved case is always handed to processing.
    • At-least-once messaging, exactly-once effect. Kafka may redeliver; every consumer's write is idempotent (insert ignores duplicates, result updates only an OPEN case).
    • Nothing silently dropped. Unreadable messages go to a .DLT topic instead of blocking or vanishing.

    The ceiling is the generator's HTTP client, not the system's work or the backend. The connection test, where the backend replies instantly and touches nothing, stops at the same line as real submissions. A native load tool (oha) then got 25,000 requests per second from the same backend on the same machine (see below).

    How a run collapses

    1. Replies slow down briefly, from about 25 ms to a few hundred milliseconds.
    2. The generator is open-loop, so it keeps sending at full rate and opens a burst of new connections for the requests now waiting.
    3. Some of those connections are refused at the backend's front door (ConnectException <- ClosedChannelException).
    4. Inside Java's HTTP client, threads queue for shared locks: the list of request timeouts, and a lock shared by all clients (AuthenticationFilter.getCache). Measured: 13 seconds of lock waiting in 6 seconds.
    5. Failed and closed sockets hold local ports: about 15,000 in TimeWait (locked 2 minutes each) and about 13,600 Bound from failed attempts. Windows runs out: No buffer space available (maximum connections reached?).
    6. Nothing pushes back, so it never recovers. The backend sits mostly idle, starved of requests.

    Ruled out, with measurements

    Kafka
    Benchmarked at about 32,800 confirmed writes per second through Docker's port (36,000 inside the container), while failing runs never exceeded 9,700 per second.
    Docker's port forwarding
    Costs about 10% and caused no stalls in the benchmark.
    Downstream work
    600k still collapsed with the case writer, outbox relay, result writer and processor all paused.
    The backend's work
    The connection test collapses at the same rate. During collapses the backend's CPU fell, with no requests in progress.
    GC pauses and CPU
    Pauses stayed short (130 ms at most, and only after the slowdown had started). Machine CPU peaked around 50–77%.

    What helped along the way

    Keep-alive and HTTP/1.1, the background report writer, -XX:-UseThreadPriorities
    Each removed a cause of collapses on the way from 100k to 550k per minute: connection limits, the generator's own stalls, and freezes from low-priority threads.
    Warm-up
    Without it, freshly started apps failed even at 500k and 550k: the first second at full rate opens thousands of connections at once.
    8 HTTP clients in the generator
    Accepted submissions at 600k rose from about 2,000–25,000 to 130,000–178,000. It degrades more gently, but the ceiling did not move.
    A separate Kafka producer for intake
    Customer requests no longer queue behind the outbox relay's bursts.

    Running a load test reliably

    • Close heavy programs, such as games, first. Everything shares one machine's CPU and networking.
    • Restart the backend, generator and processor after code changes, from IntelliJ. DevTools auto-restart is off, so a recompile never restarts the backend mid-run.
    • Use a 30-second warm-up.
    • After a failed run, wait about 2½ minutes for locked ports to clear. Check with powershell -Command "(Get-NetTCPConnection -State TimeWait).Count"; it should be a few hundred.
    • Never take thread dumps of the generator during a run. Each dump freezes it, from a tenth of a second up to 12 seconds, and the bursts afterwards caused failures on their own. Use Java Flight Recorder instead (jcmd <pid> JFR.start settings=profile), which costs about 1–2%. Kafka's own message timestamps also show its writes per second after the fact.
    • Each app writes its own GC log: gc-backend.log, gc-generator.log, gc-processor.log, set in the VM options.
    • To isolate a layer, use the Connection test toggle (no work behind the backend) or untick Process submissions after intake (intake only).

    Going further

    • Run the generator on another machine. Benchmarking guidance warns that a load generator on the server's machine competes with it and often becomes the real limit. Spring Boot on Tomcat is commonly measured at 30,000+ simple requests per second with native load tools.
    • Measured with a native load tool: oha drove /api/cases/noop on the same machine at 10,000, 15,000 and 20,000 requests per second with 100% success (about 3–4 ms on average), and at 25,210 per second flat out. The backend's web server is not the limit: the generator's Java HTTP client is. Try the generator's Jetty HTTP client option to see how far a different client gets.
    • Add back-pressure: an in-flight cap in the generator, or the backend's Load shedding toggle (fast 503s, counted as Blocked and resendable later). They don't raise the ceiling, but can turn the collapse into a measurable, recoverable overload. The effect of load shedding at 600k has not been measured yet.
    • Raise Windows' outgoing-port limits (administrator): netsh int ipv4 set dynamicport tcp start=10000 num=55535, and TcpTimedWaitDelay of 30 in the registry. This gives about 13 times more connection churn before ports run out.

    Generator

    Plays the customers. Submissions are spread over 8 independent HTTP clients (generator.http-clients), each with its own network thread and connections. One Java HTTP client does all its network work on a single thread, which choked at about 10,000 requests per second. It is open-loop: submissions are sent on a fixed schedule whatever the backend's speed, as real customers would, each on its own virtual thread. Only one run at a time; the latest run stays in memory and every run is written to reports/<runId>.jsonl.

    Run settings

    requestsPerMinute, durationMinutes, endless
    Up to 1,000,000 per minute, for up to 60 minutes. With endless ("Run until stopped") the run keeps going until stopped and the duration is ignored. Memory stays flat either way: submission n's ID is the run id plus n, so no list of submissions is kept, and only outcomes other than accepted are stored.
    maxInFlight
    Optional cap on submissions awaiting a reply; above it a submission is skipped, not queued. Null means no cap.
    submissionMode
    KAFKA posts to /api/cases and expects 202; DIRECT posts to /api/cases/direct and expects 201 (or 200 for a retry of an already saved case); NOOP (the "Connection test" toggle) posts to /api/cases/noop, warm-up included, and expects 202 with nothing stored.
    httpClient
    JETTY is the default. JDK: Java's built-in HttpClient, spread over 8 instances; it collapses near 10,000 requests/s. JETTY: Jetty's HttpClient as 8 instances, each with its own network thread and waiting line, together at most 2,000 connections to the backend; extra requests wait in short queues (10,000 in total) instead of opening new connections, and a request with no room is skipped, never sent (generator.jetty.*). With a single instance, a large backlog left nearly all of Jetty's worker threads queued on its one waiting-line lock. The pool is fixed: with a warm-up, Jetty opens all its connections gradually over the warm-up's second half (opening hundreds at once at the switch was refused by the backend's accept queue), and neither side ever closes them for being idle. With a 30 s idle timeout the pool shrank during calm periods, and the next brief slowdown opened 874 connections in one second, of which about 2,750 requests were refused. Outcomes are classified the same either way.
    retryEnabled
    Resend submissions whose outcome is unknown. Off by default.
    warmupSeconds
    Before the measured run, ramp from zero to the full rate over this many seconds against POST /api/cases/warmup, which goes through the same path as a real submission, Kafka write included, but to a topic nothing consumes, so no case is created. That is rate × seconds ÷ 120 requests, counted separately. The run then starts at full rate on already open connections, with warmed-up code and a warmed-up Kafka producer. 0 (default) starts cold, like a sudden spike.

    Outcomes

    Accepted
    The expected status with matching fields.
    Failed / mismatched
    A definite answer that was not acceptance: 4xx, or a reply with the wrong fields.
    Unknown
    Timeout (15 s), connection error, or 5xx. The case may or may not exist; only the checker can tell.
    Skipped / not sent
    Never sent: over the in-flight cap, or the run was stopped first.
    Blocked
    Turned away by the backend's load shedding: a 503 with Retry-After, meaning "busy, nothing stored". Unlike Unknown, it is a definite answer, so it is safe to resend. It is never retried automatically, even with retries on, so the run stays exactly its set length.

    Resending blocked submissions

    After a run, Resend blocked (POST /api/runs/{id}/resend-blocked) sends every still-blocked submission again, at the run's rate and with its original clientRequestId. It is a separate pass, not part of the measured minute. Each new outcome replaces Blocked in the run's counts, and the checker sees the final state. Progress shows live, and a summary is saved as reports/<runId>.resend-<n>.json. Press it again for any that get blocked a second time; Stop ends a pass early.

    Retries

    With retries on, an unknown outcome is resent with the same clientRequestId, up to 5 attempts in total. Waits double from 0.5 s to a cap of 8 s, each randomised between half and all of its value so clients that failed together do not retry together. A submission keeps its in-flight slot until its final outcome. Rejections are never retried. Tune with generator.retry.max-attempts, base-delay and max-delay. Retries are safe because the backend is idempotent, but they add load: under sustained overload they can deepen it.

    Checker

    Reconciliation: after a run, it streams the backend's ledger of saved cases for the run (GET /api/simulation/cases/ledger) and compares it with the outcome the generator recorded for every submission. It runs automatically once processing settles, can be repeated, and writes reports/<runId>.check.json.

    Accepted: processed / awaiting / missing
    Missing is the alarming one: the client was promised a case that does not exist. Checked too early, it may still be waiting in Kafka.
    Unknown: saved anyway / never arrived
    Shows what "unknown" really meant. Saved anyway: the reply was lost, not the case.
    Blocked: total / saved
    Submissions still blocked after any resends. "Blocked but saved" should always be 0: the backend turned them away before doing anything.
    Rejected but saved, unexpected
    Should always be 0: a case the client was told failed, or one it never sent.

    Verdict: Consistent (every accepted case saved and processed), Still processing (no problems, some still OPEN), or Discrepancies found.

    The checker lives in the generator because only the client knows what it was promised. It reads the system's side through the backend's API, not the database, so it audits from the outside. A separate application would add a process without adding independence.

    One JSON object per line: run (settings), plan (the planned count and how IDs are formed), result (only submissions that were not accepted), notSent (the range never sent), second (per-second counts, latency avg, p99, max, and connections opened and closed) and summary.     Backend

    Spring Boot service that owns the cases and outbox tables. It is the only application that touches PostgreSQL.

    Public API

    POST /api/casesKafka intake. Waits only for Kafka to confirm the message, then replies 202 with a Location header for the status lookup. 503 if Kafka does not confirm within 10 s.

    Inside

    Load shedding
    Off by default. When on, a filter that runs before anything else (security, parsing, Kafka) lets at most maxConcurrent submissions be worked on at once (POST /api/cases, /direct, /noop; never the warm-up). Any beyond that get 503 with Retry-After: 1 immediately. The Retry-After header is the contract: nothing was stored, so it is safe to resend. A 503 without it (Kafka did not confirm) still means the outcome is unknown. A restart turns it off.
    Request handling
    Tomcat with a virtual thread per request (spring.threads.virtual.enabled). Before that, the 200-thread pool ran out around 600k per minute, because every request thread waits for Kafka's confirmation. Up to 8,192 connections plus a queue of 2,000 waiting to be accepted, and connections are kept alive for the whole run. DevTools auto-restart is off, so a recompile never restarts the backend mid-run.
    Kafka producers
    Two, each with its own buffer, network thread and connection. backend-intake carries customer submissions and warm-ups, where every request waits for its own confirmation. The other carries background work: the outbox relay's bursts and dead letters. A producer has exactly one network thread, so customer traffic never waits behind the relay.
    Submission consumer
    Group case-writer, 3 threads, batches of up to 500 from cases.submitted. One SQL statement per batch inserts the cases (duplicates ignored) and their outbox rows. Unreadable messages go to cases.submitted.DLT.
    Outbox relay
    Every 100 ms, claims up to 1,000 outbox rows (FOR UPDATE SKIP LOCKED), publishes them to cases.saved keyed by case ID, waits for Kafka, then deletes them. A crash before the delete republishes; the processor tolerates that.
    Result consumer
    Group case-result-writer on cases.processed. Records status, category, team and attempts, only on cases still OPEN, so a redelivered result changes nothing. Unusable results go to cases.processed.DLT.
    Pausing downstream work
    GET/PUT /api/simulation/pipeline (local only) pauses the case writer, the outbox relay and the result writer, for experiments that isolate intake. The dashboard's "Downstream processing" toggle drives it together with the processor's. Nothing is lost while paused, and a restart turns it back on.
    Status constraint
    On startup, the cases_status_check constraint is rebuilt from the status enum, since Hibernate never updates one it created.

    Processor

    A separate Spring Boot application that works purely through Kafka: it reads cases.saved, simulates the work, and publishes each result to cases.processed. It has no database access; the backend records results.

    Concurrency

    Six Kafka consumers (one per partition), each on its own thread, fetch up to 2,000 messages and start every case on its own virtual thread, up to 20,000 in flight. Cases finish in any order, so a slow case never holds back the rest. Per partition, the committed offset only advances to the oldest case still running: after a crash, unfinished cases are redelivered and none is skipped. When the in-flight limit is reached, consumers pause fetching and the backlog waits in Kafka.

    Simulated work

    Each case's plan is derived from its clientRequestId, so a redelivered case behaves the same way. Defaults (caseroute.processing.*):

    • Takes 0.5 to 1.5 s (mean 1 s); 1% are slow and take 10 s.
    • 2% chance per attempt of a transient error, retried after 500 ms, up to 3 attempts; exhausting them fails the case.
    • 0.1% fail permanently.
    • Routed by category: Billing Support, Technical Support or Account Services.

    Failed cases are also copied to cases.saved.DLT with the reason in a header. The work is Thread.sleep: it models waiting on other systems, not CPU, so throughput is roughly in-flight cases divided by time per case.

    Port 8083 (local only); GET /actuator/health. GET/PUT /api/pipeline pauses or resumes fetching from cases.saved: cases already in progress finish, and the backlog waits in Kafka. Driven by the dashboard's "Downstream processing" toggle.
